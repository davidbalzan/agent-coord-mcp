- [ ] (P2) **The live bus executes from a mutable dev checkout** — every agent's MCP server and every `tmux-push` pusher resolves to the primary checkout (`resolvePusherPath`, and the user-scope MCP config's absolute `dist/server.js` path), regardless of which git worktree that agent works in; worktrees isolate editing, not execution. SHARPER SIGNATURE, captured on main right after the Phase 8 merge (2026-07-28): the run reported `# tests 186 / # pass 182 / # fail 0 / # skipped 0 / # cancelled 0` — the runner's OWN totals do not add up, four tests counted but landing in no bucket. So this is not "four tests failed to run" and not a glob problem; it is the reporter losing results, which also means a count-of-`# tests` guard does NOT catch it (that line read the full 186). The guard must compare PASS, not TESTS. Both prior sightings fit: 119/115 and 145/141 were also pass-vs-tests gaps of exactly 4, misread at the time as short runs. **FIRST HARD TRACE, 2026-07-29** — caught twice in a fresh standalone clone (202 tests / 198 pass / 0 fail / **4 cancelled**), so the missing four are now accounted for rather than lost, and the runner names them: all four are `failureType: 'cancelledByParent'` in `test/doctor.test.mjs` (the reaper block from :216 onward), each with `error: 'Promise resolution is still pending but the event loop has already resolved'` and `signal-exit` on the stack. **I read that stack frame as proof the process was being KILLED. It was not — see the resolution below; `signal-exit` patches `process.emit`, so it appears in ANY emit stack and is evidence of nothing.** **RATE MEASURED, AND IT IS NOT RARE** — clean `origin/main` @ 331add0 in a standalone clone: **2 of 8 full runs failed** (25%), independently corroborated by `david-worker-2` at 2 of 10 single-file runs and 2 of ~9 full-suite runs in a separate worktree. It reproduces **in isolation too** (`node --test test/doctor.test.mjs` alone), which corrects an earlier reading of mine that called it parallel-only after three clean isolated runs — three runs could not distinguish "never" from "one in four". PROMOTE TO P1: `check-test-count` correctly catches it (205≠209), so roughly a quarter of all green work now fails its gate on a coin flip and reads as the author's regression. Every gate verdict issued while this stands is suspect in one direction — a FAIL may be noise. **RESOLVED 2026-07-29 — davidbalzan/agent-coord-mcp#31, and the cause is NOT what this entry spent three sightings assuming.** `david-worker-2` instrumented every process in the test tree (preload tracer, once+re-raise so `signalCode` semantics survive): the dummy child takes doctor's SIGTERM correctly, and the TEST PROCESS TAKES NO SIGNAL AT ALL — just `beforeExit` 6ms later. Nothing kills the runner; its event loop DRAINS. Root cause is a missed-event race at `doctor.test.mjs:268`: `doctor({fix:true})` SIGTERMs the dummy mid-call, the child's `'exit'` fires during doctor's remaining awaits, and a `once("exit")` attached AFTERWARDS waits forever on an event that already happened — child dead, no live handles, loop drains, every remaining subtest in the file reports `cancelledByParent`. The ~6ms window is the coin flip. Fix: `waitForChildExit` guards on `exitCode`/`signalCode`, which node assigns BEFORE emitting `'exit'`, so the guard cannot itself race. Verified by mutation (guard removed → `not ok 7` by name, not a silent cancel) and by rate: 25% base → 0/43 for the author, 0/32 independently at the gate, combined p≈1e-9. **Lesson worth more than the fix: every earlier reading here — "reporter losing results", "process death", "signal-exit proves a kill" — was an inference dressed as a finding. The one that resolved it went and MEASURED which processes received signals.**
